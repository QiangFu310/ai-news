### 2026-11-24 · Deep Dives & Analysis

- **[给 Transformer 残差连接"超频"](https://research.google/blog/supercharging-transformer-residual-connections/?utm_source=tldrai)**（4 分钟）— Google 的 DeepCrossAttention（DCA）把残差连接改成动态路由：每一层可以从前序层里挑选并组合特征，而不是只接收上一层的固定输出。这样能减少信息稀释，在参数减少 30–40% 的情况下保持甚至超过原模型质量；在 C4、LM1B 等大数据集上收敛更快、困惑度更低，额外参数开销极小。它代表了一条与"堆更多层"不同的扩容路线：让深度连接变成可学习的路由。

- **[我以前编排 Agent，现在我编排"编排器"](https://www.nijho.lt/post/orchestrating-orchestrators/?utm_source=tldrai)**（24 分钟）— 作者描述 MindRoom 的工作方式：把多个模型放进同一个"房间"，同时管理最多 40 个并发会话，靠极少的子 Agent 和低 token 开销维持上下文切换。界面是卡片式的，按任务状态组织，而不是传统聊天列表。核心经验是：多 Agent 系统的瓶颈往往不是模型数量，而是上下文搬运与状态管理；把"编排器"本身当成一层可复用基础设施，比不断加子 Agent 更有效。

### 2026-11-24 · Engineering & Research

- **[OpenAI 与 Cisco 推出 Shirudo](https://openai.com/index/introducing-shirudo/?utm_source=tldrai)**（5 分钟）— Shirudo 是两家公司联合开源的 Linux 安全运行时：在团队滚动打补丁期间，用临时"盾"阻断针对已知漏洞的利用，不必重启服务。它基于 eBPF 在内核层观察并拦截可疑调用，适合那些"不能停"的数据库、消息队列与生产服务；属于把 AI 生成防护策略与系统级强制执行结合的一次工程化尝试。

- **[递归自我编辑：LLM 为自己的权重写补丁以自我提升](https://arxiv.org/abs/2611.29513?utm_source=tldrai)**（1 分钟）— 论文提出 SELFWRITE：不再由梯度下降写权重更新，而是让模型自己写。每一代模型先在全新训练题上复盘自己的推理，再在持久 Python 会话里检查自身权重与激活，最后写出一段程序，用白盒原语为自己构造低秩权重编辑。它能在完全不做梯度更新的情况下，提高门控准确率与一个训练循环从未见过的留出集准确率；意义是"模型改自己"从比喻变成了可执行的程序合成问题，但也带来可审计性与安全边界的新难题。

## Claude Dev 博客

- **[2026-11-24] [用 Claude Code 把 PR 收尾工作做完的实用指南](https://claude.dev/blog/the-work-after-you-open-a-pr/)** — Addy Osmani 写给"团队用 GitHub、但自己没有管理员权限"的开发者和技术负责人：PR 打开之后的 CI 失败、评审意见、主干合并冲突，都是打断心流的小任务，可以交给 Claude Ship 的三个 Agent 接管。文章给出从个人到团队的分阶段落地路径。

  **个人用法**：先在推送前跑 `/code-review`，它检查分支提交与未提交改动中的正确性 bug；`high` 提高召回、`--fix` 直接改工作区、`--comment` 把发现发到 PR、`ultra` 在云端做更深评审（需 claude.ai 登录、可能单独计费）。随后用 `/ship` 处理下一个 PR：它会像 `git add -A` 一样提交待提交改动（尊重 `.gitignore`）、建分支、以你的身份推送到 GitHub 并开 PR、跑一次代码评审并修掉它认为有效的问题，然后最多盯 7 天，处理失败检查、冲突与评论，PR 合并或关闭即退出。注意它不会提交 `CLAUDE.md`、`REVIEW.md`、`.claude/`、`.github/`、密钥样式文件或规则文件；在公开仓库里也不会替你提交，需要手动先 commit。

  **盯 PR 的边界**：watch 在本地以你的身份、你的额度运行，合上电脑就停；需要 `gh auth login`，只盯你自己开的 PR，不能在 bypass-permissions 模式下运行，Windows 上只开 PR 与评审、watch 不启动。它会把小修直接做掉、大改（重新设计 API、无法解决的安全问题）升级给你，同一问题最多推 3 次就报告尝试过的方案。作者特别提醒：watch 会把主干合进你的分支并运行测试，因此能往主干合并的人理论上就能在你机器上执行命令，只应在完全信任协作者的仓库里本地运行。

  **把重复意见变成规则**：同一评审意见出现两次，就写进 `CLAUDE.md`（本地 `/code-review`、Code Review、PR Steward 都读）或根目录 `REVIEW.md`（只给 Code Review/PR Steward 读）；反复出现的启动步骤写进 `.claude/skills/verify/SKILL.md`；PR 维护惯例写进 `.claude/skills/steward/SKILL.md`。团队的原则是"同一模式至少在 2 个 PR 上重复"才立规则，并由人批准加规则的 PR。

  **团队推广**：先保护默认分支（要求最新推送上有审批、Claude App 不在 bypass 名单），启用 Code Review，以 Manual 模式启用 PR Steward（评论 `@claude steward` 触发），再用 `.claude/approvals.yml` 建 observe 模式审批策略——`seats` 规定需要几人批准、作者可占一席，`verdict: claude: comments` 表示 Claude 只评论不批准，多条规则取最严格者。观察一两周后对比"Claude 会怎么判"与真实评审行为，再移除 `mode: observe` 进入强制执行，并把 Claude Approvals 检查设为 required。作者强调 Claude 的批准在 GitHub 上算真实批准，必须和分支规则一起读；所有现有测试、扫描器与人工评审都不能撤。
